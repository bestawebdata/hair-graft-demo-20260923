# 日程調整・運営管理デモ

2026年9月24日。先生・医療機関・患者さんの予定をまとめ、櫻庭さんの照合作業を減らすための操作試作です。

同日、本人の希望から案内候補と次の対応を提案する「受付・案内順」を追加しました。[8人の受付例と操作方法](RECEPTION_DEMO.md) を参照してください。運営画面の人数は、参加可能かつ手続きへ進めると回答し、相談・案内停止を希望していない方を集計します。

## 運用の考え方

日程が決まる前からエントリーを受け付けます。同時に、先生と提携医療機関が対応できる日時を集め、重なる時間帯を候補にします。運営が期限付きで仮押さえすると、患者さんに会場と日程を提示して参加希望を募れます。参加希望と開催条件がそろった日程を、運営が確認して開催確定に進めます。

患者さんは地域の第1〜第3希望を入力せず、大阪・伊丹・神戸の候補を見て都合を回答します。行けない会場や日程に自動で割り当てません。予定が合わなければ登録を残し、次の案内を待てます。参加人数や「あと何人」は運営画面だけに表示します。

最低5人はユーザー指定の運用目安です。開催枠5時間・1会場の受け入れ5人・先生は1日1会場という条件は、デモを動かす仮設定です。医学的な施術時間や実際の受け入れ能力を意味しません。開催確定と、診察・説明を経た個々の施術予約は分けています。

## 3分で体験する

1. 「運営管理」で大阪10月10日の参加希望が4人であることを確認。
2. 「患者画面を開く」から、デモ患者05として「参加を希望する」を選び、「この回答を反映する」を押す。
3. 運営画面に戻ると5人になり、「参加者を確認して開催確定」が有効になる。対象者を確認して確定する。
4. 「案内文を見る」で通知の文面を確認する。実送信はしない。
5. 「最初から試す」で戻し、「先生・医療機関」から先生の10月18日の終了時刻を14:00へ変更して保存する。神戸の新しい候補が出る。
6. 新しい候補の「仮押さえして募集する」を押し、期限を設定する。患者さんの画面にも日程が増える。
7. 「基準日を1日進める」で期限の翌日まで進めると、仮押さえが失効し募集を停止する。回答履歴は管理側に残る。

固定シナリオの基準日は2026年10月1日、入力できる日は10月10日・11日・17日・18日です。現在時刻に依存せず、打ち合わせで繰り返し再現できます。「架空の新規エントリーを追加」はダミー登録を増やすボタンで、氏名・連絡先の収集はしません。

## 実装したもの

| 機能 | このデモでの動作 |
| --- | --- |
| 先生・施設の予定 | 各回答者の時間帯を編集し、重なりと開催枠を自動照合 |
| 仮押さえ | 回答期限を設定。同日の別会場を二重に確保しない |
| 患者の回答 | 参加希望・未定・都合が合わないを反映。変更しても重複計上しない |
| 開催判断 | 目安人数と空き時間を再確認し、対象者を選んで確定 |
| 重複防止 | 他の開催で案内対象になった患者を新規開催の人数から除外 |
| 予定変更 | 確保済み時間が失われたら「要再調整」とし、新規回答を停止 |
| 期限管理 | デモ日付を進めると、期限翌日に失効。解除・失効の回答履歴を保持 |
| 管理 | 架空のエントリー、開催状況、操作履歴、案内文を一覧表示 |

`core.js` が照合・状態遷移、`app.js` が画面、`styles.css` が見た目です。予定と運用条件は `core.js` の `seed()` に分離しています。純粋な照合関数と画面を分け、本番でサーバー側処理へ移しやすくしています。

## 本番化に必要な接続と実装

まず先生と病院が専用画面から「対応可能な時間」を入力する方式なら、カレンダー製品をそろえずに始められます。その後、利用しているカレンダーに合わせて連携を追加できます。Google Calendarには空き時間照会とイベント作成APIがありますが、このデモでは呼び出していません。[空き時間照会](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query)、[イベント作成](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert)。

カレンダーに予定がないことと、その治療を受け入れられることは別です。担当者が指定した対応可能時間から既存予定を除き、会場・スタッフ・設備・準備や移動時間を含めて照合します。権限不足・取得失敗・同期が古い場合は、空き時間とみなさず確認対象にします。

本番では次を実装します。

- 先生・施設担当・運営・患者それぞれのログイン、閲覧範囲、同意管理。施設は自施設の開催に必要な情報だけを見る。
- 共通の登録台帳とデータベース。LINEとWebからの登録を同じ登録IDで扱い、患者本人が自分の回答だけを変更できるようにする。
- サーバーでの再照合と同時更新制御。先生・施設の枠を一体で確保し、二重確定・重複通知を防ぐ。カレンダー書き込みが片側だけ成功した場合は取り消し・再調整する。
- バックグラウンドの期限処理、変更検出、回答依頼・リマインド・開催決定の通知。運営画面を閉じていても動作し、未達を管理する。
- 実際の仮押さえを各カレンダーへ反映する権限と期限、確定・解除手順。デモでは運営ボタンで仮押さえするが、施設が事前承認した枠なら自動化する余地がある。
- 確定後の辞退・変更・キャンセル・繰り上げ・再調整。履歴を残し、変更を患者に伝えてから新日程へ進める。
- 個別の診察・説明・施術予約の状態管理。人数到達だけで施術可否を判断しない。

現在のGitHub Pagesは説明画面の配信です。実患者データ、鍵、予定の原本を公開リポジトリに置きません。本番の保存・認証・通知処理は専用のバックエンドへ接続します。
