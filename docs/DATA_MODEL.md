# 将来のサービス構造

現在は静的な集客LP・LINE画面に、日程調整の操作デモを追加しています。医師・会場・地域・症例は表示設定を分離し、将来の管理サービスへ移せるようにしています。以下は本番サービスの設計案であり、バックエンドが稼働していることを意味しません。

| 管理対象 | 主な項目 | 関係 |
| --- | --- | --- |
| 医師 Doctors | ID、氏名、確認済み経歴、対応治療、担当可能日、承認履歴 | 開催・医療機関に紐づく |
| 医療機関 Facilities | ID、契約状態、正式名、住所、連絡先、地域、施術条件 | 開催と診療の責任主体 |
| 地域 Regions | ID、名称、対応範囲、開催検討条件 | 希望登録を集約 |
| 希望登録 Interests | ID、氏名、年代、居住地域、連絡先、治療経験、同意日時、対応状態 | 案内対象開催に紐づく。最新方針では希望地域の順位を必須にしない |
| 対応可能時間 Availability | 回答者ID、日付、開始・終了、受け入れ条件、更新日時 | 医師・施設の時間帯を照合 |
| 開催 Events | ID、地域、医師、医療機関、予定日、受付枠、調整状態 | 医師と医療機関の確定後に案内 |
| 仮押さえ Holds | 開催ID、期限、状態、外部カレンダー参照、版番号 | 先生・会場の枠を一体で確保・解除 |
| 日程回答 Responses | 開催ID、登録ID、参加希望・未定・不参加、回答日時 | 開催と登録者の組み合わせで一意。変更は上書きと履歴で管理 |
| 案内対象 Participants | 開催ID、登録ID、確定・取り下げ状態 | 他開催との二重確定を防止 |
| 予約 Reservations | ID、登録ID、開催ID、診察状態、本人確認、予約状態 | 希望登録から本人の意思確認を経て作成 |
| 症例 Cases | 匿名ID、治療内容・回数、費用、リスク、掲載許可、医師確認 | 経過写真を継続追加 |
| 経過写真 Observations | 症例ID、撮影日・経過時点、撮影条件、画像、注記、承認状態 | 症例に1対多で紐づく |

運用状態の例：希望登録と医師・施設の予定収集を並行 → 候補照合 → 期限付き仮押さえ → 参加希望回答 → 運営が開催確定 → 個別案内 → 診察 → 予約確定 → 施術 → 経過観察。人数に達しただけで予約・施術を自動確定しません。

操作デモでは開催を `held / confirmed / expired / cancelled` で管理し、現在の空き時間との矛盾は「要再調整」として判定します。本番では開催・枠確保・案内対象の更新をサーバー側のトランザクションで管理し、通知とカレンダー反映を重複しない処理として実装します。詳しくは [日程調整デモ](COORDINATION_DEMO.md) を参照してください。

公開側は承認済みデータだけを表示し、個人情報を含む希望登録・予約、同意記録、原画像、監査履歴はアクセス制御された管理側に分けます。

## 現在のフォーム

実送信・API・DB・Cookie・localStorage・sessionStorage・外部アクセス解析はありません。入力と確認中のデータはDOMとメモリ内のみです。完了時に氏名・連絡先を消去します。希望地域の表示は「消去して戻る」または再読み込みで消えます。地域別の実件数も蓄積しません。

## 症例の追加

既存パンフレットの比較写真は `brochureGallery` とその `records[].observations` で管理します。ユーザー確認に基づく写真使用の状態を `publicationAuthorized` に記録し、出典・原資料内の位置・経過表記・画像の寸法を保持しています。未提示の撮影条件や施術回数まで確認済みとするデータは作っていません。

テンプレートの `observations` は配列です。同一条件で撮影した経過写真を後から追加できます。画像URLはローカル `assets/cases/` 配下の画像だけを許可し、説明をエスケープして表示します。承認状態と必要説明が欠けた症例は非表示です。実運用ではフラグを直接編集する方法から、権限管理された承認処理へ置き換えます。
